## Multi-agent software engineering

### How I coordinated and verified the work

I kept product decisions and approval with me and used a coordinator to dispatch work, integrate commits, and reconcile evidence. I approved the Mission Brief and PRD before the design package was finalized. The Technical Design Document defined interfaces and failure behavior, and the Requirements-to-Tests map gave each acceptance criterion a verification path. Independent package review preceded approval of the exact artifact bytes. A separate authorization started implementation. That sequence gave the agents a clear point at which they could act autonomously within the approved scope. [Workflow runbook](../workflow/agents/README.md)

For the multi-agent question-generation run, one agent owned the implementation and unit tests and another owned acceptance tests. The acceptance author committed its interpretation before seeing implementation changes. The two writers then worked in separate worktrees with disjoint paths, while the coordinator serialized integrated database and browser checks. Both the single-builder and multi-agent candidates later received independent functional, standards, and security reviews. I checked the pattern against dispatch receipts, session identities, commit ancestry, the frozen interpretation, and command results. The role files supplied instructions to generic agents. Worktrees isolated writes, while the read boundaries still depended on agent compliance. Two writer receipts differed from the intended packet by a final newline, and the host log could only corroborate dispatch because its message arguments were encrypted. ### How I resolved conflicting evidence

I used the approved requirement and a reproduction to settle discrepancies. The functional reviewer found that the multi-agent candidate rejected an oversized provider response only after reading the whole body. Existing tests accepted a `503` from a completed stream, even though the requirement called for cancellation as soon as the selected content crossed the cap. The coordinator reproduced the failure with EOF withheld, the acceptance author added a regression, and the implementer repaired the transport. When acceptance locators assumed wording the spec left open, the coordinator supplied the rendered facts while preserving the expected behavior. The later decision to support Python topics at any difficulty changed the approved product scope, so I recorded it as a separate requirements amendment. [Independent reviews](../workflow/experiments/MP4-D2-F01/multi/reviews.md) · [Context and resource measurements](../workflow/experiments/MP4-D2-F01/multi/measurements.md) · [Topic difficulty amendment](../docs/mission-brief/MP4-D2-F01-topic-difficulty-amendment.md)

The final blind reviewers also disagreed about severity. The single-builder candidate added an unapproved 128-character limit on model metadata. The delivery reviewer rated it a minor interface issue, while the security and standards reviewer rated it a blocker. I kept both verdicts and recorded that the counterexample came from source inspection. For a release decision, I would check the approved interface, run the counterexample, and resolve its user impact before accepting the revision.

I also learned to identify which layer produced a failure. After publication passed local verification, an owner review flagged that a background session refresh could reset an instructor's or learner's loaded question list. Holding the session response in a browser test reproduced the reset while the check was pending. The fix kept same-user pages mounted and cleared the list when the session changed accounts. Conversely, the F01 pull request's database failure came from a test that hard-coded the experiment's database name. I reproduced it, repaired the check to use the validated target, and ran the focused case against both database names. These two cases changed what I ask for in a handoff. I want to know whether a check exercised the app state, the test harness, or the hosted runtime, and what it actually observed. ### When coordination paid off

Parallel work still had dependencies. The F01 implementer started after the interpretation freeze. In the earlier synthetic pilot, the second writer started about 85 seconds late because setup agents occupied the available slots. During F02 publication, I split backend and frontend ownership, with contract exports landing before the frontend consumed them. Unrelated F01 processes already owned the default test ports, so F02 used separate loopback ports. A host usage limit interrupted the publication builders and later interrupted grading reviewers. I preserved partial work and resumed from scoped handoffs. The F01 multi-agent monitor captured about 511 seconds of construction dependency wait. Idle time and individual workload were unavailable. [F01 monitor](../workflow/experiments/MP4-D2-F01/multi/resources/report.md) · [Pilot results](../workflow/evaluations/royden/pilot/REPORT.md) · [Publication log](../logs/royden/MP4-D2-F02.md) · [Grading measurement notes](../workflow/evaluations/royden/MP4-D2-F01-grading/measurement-notes.md)

ZhengHao's learner-workspace reflection helped me distinguish sequential specialization from parallel construction. His tester started after the implementation handoff. My F01 acceptance author and implementer overlapped after the interpretation was frozen. I would keep the independent check in either pattern and decide separately whether the construction work can be split. In grading, independent review surfaced a schema-valid reply that could falsely confirm a score and a peer-tab session change that could leave private grading content visible. Those findings justified the review effort. ## Context engineering and resource-aware use

### What I supplied and what agents retrieved

I put durable constraints and routing in `AGENTS.md`, the gate and verification procedures in `mp4-feature-delivery` and `verify-app`, and the immediate assignment in a fresh role packet. Up front I supplied the goal, approval and base commit, owned paths, interfaces, access limits, and evidence expected at handoff. I linked the complete applicable approved package and used targeted retrieval for source, logs, and diagnostics. This helped keep Dev 2's planning artifacts out of Dev 1's review context while sharing the relevant code, tests, and contracts. I checked the skills with structural validation and independent scenarios. One scenario checked that an approved-looking header could not substitute for missing approval provenance and a mismatched design hash. [Repository instructions](../AGENTS.md) · [Assignment template](../workflow/templates/assignment.md) · [Workflow implementation review](../workflow/evaluations/royden/implementation-review.md)

More context sometimes made the next decision harder. In F01 the coordinator read a long historical ledger that included superseded metrics. Oversized outputs were truncated and had to be read again. Independent agents did need to reread the same requirements, but the ledger reread and truncation recovery had no comparable verification value. In a `notes.md` or handoff, I would put the current approved version and base/head first, followed by decisions and their rationale, owned paths, the last integrated command and result, outstanding failures and evidence gaps, resource ownership and cleanup, and the next authorized action. The pilot's parallel handoff lost a point because I omitted the exact final integrated command even though I reported the passing count. A concise decision record also gives a replacement reviewer something concrete to recheck after an interruption. ### Where the resources went

I used the workflow monitor to deduplicate response usage, record explicit waits and retries, and keep raw telemetry outside Git. Coordination was the largest recorded task across the authentication, publication, and grading reports. The F01 coordinator accounted for about **55%** of multi-agent tokens, including integration, verification, and evidence production. The pilot also incurred one-time workflow and instrumentation costs. I tried scoped repair packets and incremental re-review after localized findings, though I have no matched estimate of the tokens saved. [Monitoring guide](../workflow/monitoring.md) · [F01 measurements](../workflow/experiments/MP4-D2-F01/multi/measurements.md) · [Authentication monitoring](../workflow/evaluations/royden/MP4-D2-AUTH/monitoring/report.md) · [Publication monitoring](../workflow/evaluations/royden/MP4-D2-F02/report.md) · [Grading monitoring](../workflow/evaluations/royden/MP4-D2-F01-grading/monitoring/report.md)

In grading, the final result of an interrupted composed-browser run was unrecoverable, so I confirmed its listeners had stopped and reran it with persistent JSON and text output. I also corrected my measurement process after locale-sensitive timestamp parsing transposed the month and day for review starts and inflated the wall interval. The coordinator recovered the original ISO timestamps and regenerated the report. These incidents make reliable evidence capture part of my resource budget. My original F01 soft estimate of 5M tokens was too low for either arm, and I would now calibrate from comparable checkpoints. [Grading verification](../workflow/evaluations/royden/MP4-D2-F01-grading/verification.md) · [Grading measurement notes](../workflow/evaluations/royden/MP4-D2-F01-grading/measurement-notes.md) · [F01 measurements](../workflow/experiments/MP4-D2-F01/multi/measurements.md)

In F01 the multi-agent run had **98.66% cached input versus 97.62%** for the single-builder run, yet it used **986,400 versus 715,952 uncached input tokens**. I would keep the shared instruction prefix stable, put task-specific material after it, and reduce repeated large tool outputs. I have no measured savings percentage from a controlled cache experiment. At the same checkpoint, reported reasoning was **42.43% versus 30.39% of output**, or **0.196% versus 0.142% of total tokens**. The multi-agent coordinator alone reported **100,152 reasoning tokens**, about **57.0% of its 175,715 output tokens** and **0.245% of its 40,868,214 total tokens**. I count cached input within input and reasoning within output. I use these observations to compare workflow usage, and billing is outside the scope of the collector. I would persist decisions, rejected hypotheses, and reproducible checks so another agent can resume from them. The savings from that practice remain unmeasured. ### What I would test next

I held `gpt-6.1-sol` at high reasoning effort across the paired F01 runs to control model variation. Grading used the default runtime models, which gave me no controlled comparison of model choices. My next experiment would compare lower effort for bounded documentation or evidence extraction with higher effort for ambiguous requirements, concurrency, and security review. I would judge each configuration against the same outcome rubric and log total and uncached input, output, retries, and elapsed time through an equivalent checkpoint. The paired F01 result came from one pair in a fixed order, with cache and host load uncontrolled. It gave me enough evidence to question routine parallel construction and a concrete way to measure when it earns its cost.

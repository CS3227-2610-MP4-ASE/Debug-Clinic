## Multi-agent software engineering

I kept product decisions and approval with me and used a coordinator to dispatch work, integrate commits, and reconcile evidence. I approved the Mission Brief and PRD before the design package was finalized. The Technical Design Document defined interfaces and failure behavior, and the Requirements-to-Tests map gave each acceptance criterion a verification path. Independent package review preceded approval of the exact artifact bytes. A separate authorization started implementation. That sequence gave the agents a clear point at which they could act autonomously within the approved scope. [Workflow runbook](../workflow/agents/README.md)

For the multi-agent question-generation run, one agent owned the implementation and unit tests and another owned acceptance tests. The acceptance author committed its interpretation before seeing implementation changes. The two writers then worked in separate worktrees with disjoint paths, while the coordinator serialized integrated database and browser checks. Both the single-builder and multi-agent candidates later received independent functional, standards, and security reviews. I checked the pattern against dispatch receipts, session identities, commit ancestry, the frozen interpretation, and command results. The role files supplied instructions to generic agents. Worktrees isolated writes, while the read boundaries still depended on agent compliance. Two writer receipts differed from the intended packet by a final newline, and the host log could only corroborate dispatch because its message arguments were encrypted. [Experiment protocol](../workflow/experiments/MP4-D2-F01/PROTOCOL.md) · [Dispatch receipts](../workflow/experiments/MP4-D2-F01/multi/dispatch-integrity.json) · [Commit record](../workflow/experiments/MP4-D2-F01/multi/commits.json)

I used the approved requirement and a reproduction to settle discrepancies. The functional reviewer found that the multi-agent candidate rejected an oversized provider response only after reading the whole body. Existing tests accepted a `503` from a completed stream, even though the requirement called for cancellation as soon as the selected content crossed the cap. The coordinator reproduced the failure with EOF withheld, the acceptance author added a regression, and the implementer repaired the transport. When acceptance locators assumed wording the spec left open, the coordinator supplied the rendered facts while preserving the expected behavior. I would take an actual change in product intent back to the owner decision and update the affected artifacts before proceeding. [Independent reviews](../workflow/experiments/MP4-D2-F01/multi/reviews.md) · [Context and resource measurements](../workflow/experiments/MP4-D2-F01/multi/measurements.md)

Parallel work still had dependencies. The F01 implementer started after the interpretation freeze. In the earlier synthetic pilot, the second writer started about 85 seconds late because setup agents occupied the available slots. During F02 publication, I split backend and frontend ownership, with contract exports landing before the frontend consumed them. Unrelated F01 processes already owned the default test ports, so F02 used separate loopback ports. A host usage limit interrupted the publication builders and later interrupted grading reviewers. I preserved partial work and resumed from scoped handoffs. I can point to those waits and interruptions, but the logs cannot establish how much agents were idle or whether an individual agent was overloaded. [Pilot results](../workflow/evaluations/royden/pilot/REPORT.md) · [Publication log](../logs/royden/MP4-D2-F02.md) · [Grading measurement notes](../workflow/evaluations/royden/MP4-D2-F01-grading/measurement-notes.md)

The paired F01 comparison changed my default. At the same start-to-reviewed checkpoint, multi-agent construction reached stronger blind delivery and deterministic test results, but took **90m 50s versus 56m 32s** and used **74.07M versus 30.28M observed tokens**. Both frozen candidates failed common acceptance. Live quality was 9/11 versus 7/11 on small samples using the same application prompt and model, so I cannot attribute that difference to how I organized the development agents. Later prompt and CI repairs were outside the frozen comparison. For the much smaller publication-guard pilot, both candidates passed all 12 held-out checks, and the parallel condition used about 46% more tokens. I would use one builder for small or tightly coupled changes, add parallel builders when contracts and ownership make work genuinely independent, and retain independent verification for higher-risk changes. For grading, that independent review surfaced a schema-valid reply that could falsely confirm a score and a peer-tab session change that could leave private grading content visible. Those findings justified the review effort. ## Context engineering and resource-aware use

I put durable constraints and routing in `AGENTS.md`, the gate and verification procedures in `mp4-feature-delivery` and `verify-app`, and the immediate assignment in a fresh role packet. Up front I supplied the goal, approval and base commit, owned paths, interfaces, access limits, and evidence expected at handoff. I linked the complete applicable approved package and used targeted retrieval for source, logs, and diagnostics. This helped keep Dev 2's planning artifacts out of Dev 1's review context while sharing the relevant code, tests, and contracts. I checked the skills with structural validation and independent scenarios. One scenario checked that an approved-looking header could not substitute for missing approval provenance and a mismatched design hash. [Repository instructions](../AGENTS.md) · [Assignment template](../workflow/templates/assignment.md) · [Workflow implementation review](../workflow/evaluations/royden/implementation-review.md)

More context sometimes made the next decision harder. In F01 the coordinator read a long historical ledger that included superseded metrics. Oversized outputs were truncated and had to be read again. Independent agents did need to reread the same requirements, but the ledger reread and truncation recovery had no comparable verification value. In a `notes.md` or handoff, I would put the current approved version and base/head first, followed by decisions and their rationale, owned paths, the last integrated command and result, outstanding failures and evidence gaps, resource ownership and cleanup, and the next authorized action. The pilot's parallel handoff lost a point because I omitted the exact final integrated command even though I reported the passing count. A concise decision record also gives a replacement reviewer something concrete to recheck after an interruption. [F01 measurements](../workflow/experiments/MP4-D2-F01/multi/measurements.md) · [Pilot results](../workflow/evaluations/royden/pilot/REPORT.md) · [Handoff template](../workflow/templates/handoff.md)

I used the workflow monitor to deduplicate response usage, record explicit waits and retries, and keep raw telemetry outside Git. The F01 coordinator accounted for about **55%** of multi-agent tokens, including integration, verification, and evidence production. In the pilot, building the workflow and instrumentation also made setup expensive. I tried scoped repair packets and incremental re-review to avoid reopening the full feature after a localized finding. I also learned to preserve command results across interruptions. In grading, the final result of an interrupted composed-browser run was unrecoverable, so I confirmed its listeners had stopped and reran it with persistent JSON and text output. My original F01 soft estimate of 5M tokens was too low for either arm. I would budget from comparable checkpoints and track recovery and evidence work explicitly. [Monitoring guide](../workflow/monitoring.md) · [F01 measurements](../workflow/experiments/MP4-D2-F01/multi/measurements.md) · [Grading verification](../workflow/evaluations/royden/MP4-D2-F01-grading/verification.md)

In F01 the multi-agent run had **98.66% cached input versus 97.62%** for the single-builder run, yet it used **986,400 versus 715,952 uncached input tokens**. I would keep the shared instruction prefix stable, put task-specific material after it, and reduce repeated large tool outputs. I did not isolate any of those changes in a cache experiment, so I have no measured savings percentage. At the same checkpoint, reported reasoning was **42.43% versus 30.39% of output**, or **0.196% versus 0.142% of total tokens** when repeated input is included. Cached input and reasoning output are subsets of those totals. I would persist decisions, rejected hypotheses, and reproducible checks so another agent can resume from them. I did not measure how much reasoning that would save. [F01 measurements](../workflow/experiments/MP4-D2-F01/multi/measurements.md) · [Evaluation protocol](../workflow/evaluations/royden/protocol.md)

I held `gpt-6.1-sol` at high reasoning effort across the paired F01 runs to control model variation. Grading used the default runtime models, which gave me no controlled comparison of model choices. My next experiment would compare lower effort for bounded documentation or evidence extraction with higher effort for ambiguous requirements, concurrency, and security review. I would judge each configuration against the same outcome rubric and log total and uncached input, output, retries, and elapsed time through an equivalent checkpoint. The paired F01 result came from one pair in a fixed order, with cache and host load uncontrolled. It gave me enough evidence to question routine parallel construction and a concrete way to measure when it earns its cost.

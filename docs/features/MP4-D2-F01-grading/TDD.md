## Data, authorization and atomic save

`AttemptGrade` has exactly one row per graded attempt. `attemptId` is a text primary key and foreign key to `Attempt.id` with `ON DELETE RESTRICT`. `score` is a non-null integer with PostgreSQL `CHECK (score BETWEEN 1 AND 10)`. `revision` is a non-null integer with `CHECK (revision BETWEEN 1 AND 2147483647)`. `savedAt` is a non-null UTC time, using the repository's millisecond timestamp representation. Absence of a row is the only ungraded state. There is no grade deletion route. Add a `(savedAt, attemptId)` index for graded ordering, and use existing ownership indexes as join entry points. Each read uses bounded explicit selects. [Prisma schema](../../../prisma/schema.prisma) · [Coding standards](../../CodingStandards.md#types-data-and-errors)

An eligible row has `Attempt.status = FINAL_SUBMITTED`. The existing database check supplies the non-null time for this filter. Instructor requests require `INSTRUCTOR` and `Attempt.exerciseVersion.exercise.authorId = session.user.id`. Learner requests require `LEARNER` and `Attempt.learnerId = session.user.id`. Apply these filters inside every list, single-record read and write. Follow the version foreign key directly, including after archive. The eligibility rule uses the finalized attempt and ownership independent of question visibility. Leave the canonical published-question checks in the browse/attempt paths in force.

The grade write is one PostgreSQL `READ COMMITTED` transaction. Select and lock the eligible `Attempt` row with `FOR UPDATE OF` the attempt, using bound parameters and the ownership join. Use the same lock for every grade write, including creation, so competing writers serialize even when the grade row is absent. This lock reads only identity and applies no attempt update. In the locked transaction read the current grade, compare revisions, then conditionally insert or update the grade and construct the validated response. The comparison and mutation are under the same lock. Keep the transaction short and report success after it commits.

| Current state and request | Committed outcome |
| --- | --- |
| No grade and `expectedRevision: null` | Create with the requested score, revision `1`, and database save time. |
| Current revision matches and score differs | Replace score, increment revision by one, and take the database save time after acquiring the lock. Use the later of the DB clock and the existing timestamp plus one millisecond, so the same attempt's save time increases even within a clock tick. |
| Current revision matches and score is unchanged | Return `200` with the unchanged grade. Preserve the timestamp and revision. The UI can acknowledge this without repositioning the row. |
| Current revision differs, including `null` versus an existing grade or a non-null value versus absence | Return `409 CONFLICT` with `NOT_APPLIED`. Compare revision before considering score equality. A stale repeat of a committed request also conflicts. |
| Matching revision is at the integer limit and score differs | Return `409 CONFLICT`, `NOT_APPLIED`, with the safe detail `path: "revision"`, `message: "The grade revision limit was reached."`. Display that terminal condition and retain the confirmed grade and entered value. |

Use the database clock at the point of the grade mutation. Return an ISO UTC string with millisecond precision. The initial save and a changed score become learner-readable on commit. A first save competing with another first save has one winner. A correction competing with another correction on the same revision has one winner. A remove operation archives the parent and leaves both the qualifying attempt and grade valid. A lost or ambiguous commit response is resolved through a fresh read. Do not retry a write from the server on an uncertain transaction outcome.

Create the grade table, constraints and index in one additive migration after the latest existing migration. Keep the table empty at rollout and apply the migration before enabling the new app code in either composition. Old app code and both existing data models continue to work against the additive schema. Roll back the application version while retaining the grade table and committed grades if necessary. A pre-migration or unavailable database yields a safe dependency failure on new routes. Rehearse both empty and representative pre-feature databases on an explicitly verified, isolated PostgreSQL target.

## HTTP interface

All routes below are under `/api/v1`. Use `DraftIdSchema` for attempt IDs, existing ISO UTC millisecond timestamp serialization, strict Zod query and object schemas, and validated response projections. Names in the shape descriptions denote JSON keys. Clients treat `nextCursor` as an opaque string.

| Method and route | Input | `200` response |
| --- | --- | --- |
| `GET /instructor/submissions` | Optional `view=awaiting\|graded`, default `awaiting`, and optional `cursor` | `{ items: InstructorRow[], nextCursor: string \| null }` |
| `GET /instructor/submissions/:attemptId` | Path ID | `{ submission: InstructorDetail }` |
| `GET /instructor/submissions/:attemptId/grade` | Path ID | `{ grade: InstructorGrade \| null }` |
| `PUT /instructor/submissions/:attemptId/grade` | JSON `{ score: number, expectedRevision: number \| null }` | `{ grade: InstructorGrade }` |
| `GET /learner/submissions` | Optional `cursor` | `{ items: LearnerRow[], nextCursor: string \| null }` |
| `GET /learner/submissions/:attemptId` | Path ID | `{ submission: LearnerDetail }` |
| `GET /learner/submissions/:attemptId/grade` | Path ID | `{ grade: LearnerGrade \| null }` |

| Shape | Fields |
| --- | --- |
| `InstructorRow` | `{ attemptId, questionTitle, learnerDisplayName, submittedAt, grade: LearnerGrade \| null }` |
| `LearnerRow` | `{ attemptId, questionTitle, submittedAt, gradingStatus: "AWAITING_GRADE" \| "GRADED" }` |
| `LearnerDetail` | `{ attemptId, question: { title, problemStatement, expectedBehavior }, code, reasoning, submittedAt, grade: LearnerGrade \| null }` |
| `InstructorDetail` | Same fields as `LearnerDetail`, plus `learnerDisplayName`, with `grade: InstructorGrade \| null` |
| `LearnerGrade` | `{ score }` |
| `InstructorGrade` | `{ score, revision, savedAt }` |

`score` is a JSON number, integral from `1` through `10`. `expectedRevision` is required, either `null` or an integer from `1` through `2147483647`. Do not coerce JSON strings. The body must contain exactly the two required keys. List queries accept only the specified optional keys, at most once each. Detail and grade routes accept an empty query only. `submittedAt` is the exact non-null attempt submission timestamp. Select only the learner's `name` for instructor detail and rows. Query projections and contracts exclude email, user records, solution and provenance fields, and numeric scores on the learner list. The learner grade poll reads only score and eligibility and carries no snapshot fields. Render stored text as text with preserved formatting and escaping. Use display components with horizontal scrolling for long code lines and wrapping for reasoning.

### Pagination and queue refresh

- Awaiting instructor rows filter for grade absence and order `(finalSubmittedAt ASC, attemptId ASC)`. Graded instructor rows require a grade and order `(savedAt DESC, attemptId DESC)`. Learner rows order `(finalSubmittedAt DESC, attemptId DESC)` for all their finals. Fetch 51, return up to 50, and emit a cursor from the last returned item only if a further item exists.
- Cursor format is unpadded Base64URL of UTF-8 JSON `{v:1,scope,at,attemptId}`. `scope` is `instructor-awaiting`, `instructor-graded` or `learner-submissions`. Validate the encoding, strict object, scope match, canonical UTC millisecond timestamp and ID. Reject invalid or over-2,048-character cursors with `400`. Keyset comparisons use the exact ordering tuple and matching database collation. Apply ownership predicates independently of cursor values. Continuations compare values and work even when the old cursor row changes views.
- Lists are current pages, with no multi-request snapshot. A concurrently inserted row or a correction that moves above a cursor appears on the next first-page load. On entry, queue view change, return from a detail, or explicit list refresh, reset pagination and fetch page one. **Load more** appends and deduplicates by attempt ID. A failed first page shows load error with retry. A failed continuation preserves existing rows and offers a retry of that continuation. A successful zero-row first page shows its distinct empty state. Clear stale list responses on view change. A successful first grade removes the row from a freshly loaded awaiting queue. A fresh graded queue orders the grade by its current save time.

### Access, transport and errors

Use the existing cookie session resolver, role guards, allowed-origin CORS and request-ID/error handling. `PUT` requires an allowed `Origin` and `application/json`. Preserve Better Auth mount order and the global JSON body limit. Browser grading requests use the existing API base, `credentials: "include"` and `cache: "no-store"`. Return `Cache-Control: private, no-store` and vary on `Cookie` in addition to existing `Origin` handling on all grading responses, including errors. Install path-scoped response headers before parsers and origin checks. Successful grading GETs always return the complete small response with `200`, even when request validators are supplied. Disable conditional revalidation for these routes only. Existing question caches and route behavior retain their existing policy. [App composition](../../../apps/backend/src/app.ts) · [Session resolver](../../../apps/backend/src/auth/session.ts)

Browser clients also send `X-DebugClinic-Actor` with the admitted user ID. A client that supplies the header gets `403` if it disagrees with the resolved user. It is an optional assertion of UI identity, with the cookie, role and row ownership as the authorization authority. Check it before data reads. Allowed credentialed CORS preflight admits this header without requiring a session and returns no submission data. Deny a foreign origin. Generate a fresh opaque server request ID for grading paths before logging, CORS or parsers. Use it in logs, response headers and error envelopes instead of copying a caller-supplied ID. Log a fixed route template or grading fallback label, method, status, request ID and safe failure category. Exclude raw path/ID, headers, input, score, code, reasoning, identity, cursor and database diagnostics. Preserve existing logging and request-ID behavior elsewhere. [Logging policy](../../../apps/backend/src/lib/logger.ts)

The existing 120-request-per-minute IP budget is shared across ordinary routes. Ten visible result views at five-second intervals would consume it before ordinary actions. For the exact compact learner grade GET, apply a dedicated 600-request-per-minute IP ceiling before session resolution, so malformed or unauthenticated traffic cannot create unbounded session work. After verifying the learner session, role, supplied actor assertion and input, apply a separate 120-request-per-minute limit keyed by the verified learner ID before reading the grade. A successful, authorized poll consumes those dedicated budgets only. Rejected session, role, actor, input and row-ownership requests also count against the existing IP budget. OPTIONS uses the existing CORS path. All other methods and routes keep the existing IP budget. The dedicated IP ceiling and per-learner budget are engineering limits for this route. Eleven active learners on one IP use about 132 scheduled GETs per minute before transitions, within the dedicated ceiling. Verify isolation and the normal-mode limits with shared-IP sessions, and record capacity beyond the tested envelope as unmeasured. A rate-limited view keeps its last confirmed state and backs off according to a valid `Retry-After`, then checks again.

Use the existing error envelope `{ error: { code, message, requestId, mutationOutcome?, details? } }`. Only the grading `PUT` requires `mutationOutcome`. A parsed, expected `NOT_APPLIED` response indicates a rejection or proven rollback. Unknown or malformed replies remain uncertain even when the HTTP status is 2xx or 5xx. Response Zod failures indicate an internal response failure and must use a safe internal error, with uncertain write status if a commit could have happened.

| Precedence and condition | Response and browser handling |
| --- | --- |
| Global forbidden origin, rate limit, malformed/oversized raw JSON | Existing `403 FORBIDDEN`, `429 RATE_LIMITED`, `400 BAD_REQUEST` or `413 BAD_REQUEST`, respectively. Global middleware can respond before session resolution. Grading PUT responses are `NOT_APPLIED` for these failures. |
| Session absent or wrong role/actor | `401 UNAUTHENTICATED` or `403 FORBIDDEN`. Discard private state on authorization loss. An allowed-origin failure on an otherwise admitted request yields `403` with the origin error message. |
| PUT missing allowed Origin or JSON media type, or invalid path parameter, query or parsed body | `403 FORBIDDEN` for missing origin, `400 BAD_REQUEST` otherwise. After session and role/actor checks, check mutation transport, then parameters and body, before any row access. The score validation outcome reads **Enter a whole number from 1 to 10.** |
| Structurally valid ID with missing, draft or foreign row | Uniform `404 NOT_FOUND` with **Submission not found**. No target identity or grade. |
| Stale expected revision after authorized final lookup | `409 CONFLICT`, `NOT_APPLIED`, **The grade changed. Check the current grade before saving.** The separate revision-limit detail is handled as terminal. |
| DB/session dependency unavailable before a write starts or rollback is established | `503 DEPENDENCY_UNAVAILABLE`, `NOT_APPLIED` for PUT. A save failure with the form still authorized permits explicit retry. |
| DB/transport fault after the write can have committed, unexpected internal failure with uncertain commit | `503 DEPENDENCY_UNAVAILABLE` or `500 INTERNAL_ERROR`, `UNKNOWN`. A missing, timed-out, lost, malformed or otherwise untrusted save reply also enters read-only reconciliation. |

Keep generic errors safe and actionable. Implement the grade route's write outcome mapping explicitly. Mark `NOT_APPLIED` for expected rejections, failure to start, or a known rollback. A transaction callback completing is insufficient evidence of commit. An indeterminate commit, exception after commit, or unknown transaction-stage failure uses `UNKNOWN`. Apply this rule to the grade PUT path only and preserve existing errors elsewhere.

## Browser flows and state

Use the existing dashboard role routes and MUI theme. Add **Submissions** linking to `/instructor/submissions`, and **My submissions** linking to `/learner/submissions`. Each row is a named link to `/:attemptId` under the corresponding list. Instructor view uses named **Awaiting grade** and **Graded** tabs with keyboard activation. Instructor detail labels the learner, question context, submitted answer, confirmed grade and entered score separately. No editor write actions appear for that submitted snapshot.

### Instructor save and recovery

Start by loading detail. Store the confirmed `InstructorGrade | null` separately from local input. Use a labelled text field with numeric input mode, trimming whitespace before checking for digits and range. Reject fractional, exponential, nonnumeric, empty and out-of-range text before sending a write. Confirmed score remains visible for invalid input, while entering an edit or while a save is pending. Store the numeric choice and the confirmed revision used by a pending request. Disable repeat submit and input edits during the pending save and reconciliation. A navigation discards unsaved grading input. No pending grade state is persisted in browser storage.

| Observed event | Next state and allowed action |
| --- | --- |
| Explicit valid **Save grade** | Send one PUT using the currently reviewed revision or `null`. Show **Saving grade…** and the last confirmed grade separately. Use a ten-second browser deadline covering the response body. |
| Current successful PUT | Display the returned persisted grade and a confirmed status. The pending input is resolved. |
| Definitive write rejection with an authorized form | Keep the entered value and previous confirmed grade. Show failure and allow explicit retry using the same known revision. If a different write wins in the meantime, the revision check still applies. |
| Stale `409` | Trigger one grade GET. On success show the latest confirmed grade and keep the entered score as an unsaved choice, even when the two scores match. Allow explicit save using the reviewed revision. |
| Unknown write outcome | Trigger one grade GET. If it returns the intended score, show that score as confirmed current. If it returns another score or `null`, show that authoritative state and keep the input as an unsaved choice. A further write requires an explicit save using the newly reviewed revision. |
| Reconciliation GET fails while still authorized | Show **Grade outcome could not be confirmed.** Retain input and the last confirmed grade as such. Enable **Check grade again** only. Its sole request is GET. The next successful check follows the original conflict or unknown-outcome rule. |
| Authorization lost or page/identity disposed | Drop private state, abort requests, and ignore every late completion. Use the existing sign-in or forbidden route for session or role denial, or the generic inaccessible submission outcome on `404`. |

A check establishes the grade current at the read. Give each check a four-second deadline covering the body. If an earlier request is still in flight on the server, a later deliberate save still compares the revision observed by the check. A timeout, conflict, retry of a check, focus event, or reconnect never issues another PUT. Serialize action handling and accept a completion only for its current request generation. A response from an older save cannot repaint a state already superseded by a check, another save or a route/session change.

### Learner result and freshness

`/learner/submissions/:attemptId` loads the private result snapshot and current grade from its detail endpoint. The result shows question context, exact final answer and **Awaiting grade** or the score, such as **8/10**. That route works for a removed question. The existing `/learner/questions/:id` uses its current question and attempt workflow. When the current authorized attempt becomes `FINAL_SUBMITTED`, mount the same grade presentation for `attempt.id` and immediately load its learner grade endpoint. The panel appears both when a final loads and after a successful finalization or existing attempt reconciliation. A draft never starts a grade read. Preserve the workspace's existing submit, retry and readonly handling. [Existing question page](../../../apps/frontend/src/pages/PublishedQuestionPage.tsx)

- Initial load shows a textual loading state. Before any confirmed grade response, failure shows **Result unavailable** and **Retry result**. For the private route, retry detail until its snapshot loads. For the published route, retry the compact grade read. After success, grade refresh failures preserve the last confirmed grade or **Awaiting grade**, add **This result may be out of date.**, and offer **Retry result**. Success clears the indication. Permission denial clears the result instead of presenting it as a connectivity failure.
- Active means the learner's authorized result route is mounted, the document is `visible`, and the browser has normal connectivity. Window focus is unnecessary for an already visible document. Read immediately on opening. Once active, start compact reads on a five-second cadence measured from request starts, with one read in flight and a four-second deadline covering headers, body and validation. Retry, online, focus and transition to visible request a read promptly. Coalesce concurrent events and permit at most one event-driven start in a rolling second per result view, with rate-limit backoff taking precedence. Continue bounded scheduled reads after transient failure. Suspend timers in hidden documents, cancel that generation's poll, and read promptly on becoming visible. Browser throttling, offline failures and rate limiting use the stale/unavailable UI until a successful read.
- With the API available, request plus validation within four seconds, and at most one second for scheduling and rendering overhead, a commit just after a grade read's database snapshot is visible by the next start plus response and render budget, at most ten seconds under these conditions. This leaves five seconds within the product limit. For each first save and correction, record a monotonic timestamp at the test transport just before it forwards the instructor PUT, a conservative lower bound on commit time. Require a successful PUT and the new score rendered in the learner's separate browser context within 15 seconds of that start. Treat success-response-to-render timing as diagnostic only. Test both learner entry points and an archived final through the private route. Run a deterministic boundary case with a commit just after a poll observes the old score. Capture elapsed times and confirm the learner used no manual refresh. A controlled-clock test verifies scheduling and cleanup. A real-time browser journey verifies the user-facing bound for the test environment.
- Keep live status text in a stable `aria-live="polite"` region. Announce changes to confirmed score, loading and recovery without re-announcing every unchanged poll. Keep controls mounted and preserve focus through automatic updates. Use semantic headings, explicit labels, visible keyboard focus, adequate contrast and layouts tested at narrow and desktop widths. Make validation and save/recovery outcomes available as text, and associate input errors with the field.

### Session and request lifetime

Keep grading memory scoped to the admitted user ID, role, session epoch and route/attempt or list view. Capture those values plus a request generation for every async action and verify them before applying a response. On a route key change, known logout, expiry, role or account change, authorization denial, or unmount, synchronously stop presenting the old grading state, abort requests and timers and dispose of private data, drafts and recovery state. Browser history restoration starts with private content hidden until session and data are verified again. Keep one request per active load or action. An aborted write can still commit on the server, so reopening always reads authoritative state before any subsequent save.

The existing role guard retains admitted question editors during session interruptions. Give the embedded grade panel its own admission and disposal check, including attempt ID. Add an explicit grading admission signal to `AuthProvider` and a grading-only background revalidation action that uses the existing session request, identity, epoch and latest-request guard. The existing provider fields and session HTTP response stay compatible. The grading guard and panel use these three states:

| Admission | Behavior |
| --- | --- |
| Verified | The current session verifies the same ID, role and epoch. The matching route may read grading data and the instructor may explicitly save. |
| Indeterminate or revalidating | On an uncertain session connectivity failure, retain only the last authorized state for the same route and epoch. Keep the last confirmed result marked stale and preserve the instructor's entered score. Keep that admission mounted through the next `/me` request, including when the provider clears its transient error. Focus, online, or the user's retry requests background session revalidation. Pause grade operations and disable writes until verified. Treat an interrupted save as uncertain and reconcile with GET once verified. Never replay it. A successful same-account check triggers a fresh grading read and keeps pending input scoped to the same attempt. |
| Invalid or never admitted | Clear private state on confirmed expiry, denial, logout, account or epoch change, or disposal. During initial load or restoration of a cached page, keep prior content hidden until both session and data are verified. A new verified account gets fresh admission. |

Scope these behaviors to the grading routes and embedded panel. Keep the existing editor and unrelated auth routes on their current behavior. [Role guard](../../../apps/frontend/src/auth/RoleRoute.tsx) · [Session state](../../../apps/frontend/src/auth/AuthProvider.tsx)
